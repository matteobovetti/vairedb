# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

The [`Makefile`](Makefile) is authoritative. Most used:

```bash
make check                 # cargo check --all — fastest feedback loop
make build                 # debug build of all crates
make test                  # cargo test --all (does NOT include tests/e2e)
make test-coordinator      # single crate (also test-core, test-common)
make fmt                   # rustfmt
make lint                  # clippy --all -D warnings
make e2e                   # build Docker images, bring up the cluster, run tests/e2e, tear down
make vdb-cluster-up / vdb-cluster-down     # keep a 1-coordinator + 5-core cluster running on localhost:5432
make coverage              # llvm-cov, HTML into coverage/
```

Running one test:

```bash
cargo test --package vairedb-coordinator --test write_sql_cl_tests -- test_name
cd tests/e2e && cargo test --test sql_command_select -- test_name    # needs `make vdb-cluster-up` first
```

`tests/e2e/` is its own cargo workspace (`[workspace]` in its `Cargo.toml`), so `make test`
never touches it. Its tests talk to a real cluster over `tokio-postgres` at `127.0.0.1:5432`
and must run with `--test-threads=1`.

Prerequisites: Rust 1.95+ (edition 2024), `protoc` (protobuf code is generated by
`crates/vairedb-common/build.rs` during `cargo build`), Docker for e2e.

PR gate and its ordering are in [`AGENTS.md`](AGENTS.md); CI (`.github/workflows/`) runs only
`check`, `fmt --check` and `clippy -D warnings` — `make test` and `make e2e` are on you.

## Architecture

VaireDB is a PostgreSQL-wire-compatible coordinator over N core nodes, each holding an
embedded DuckDB with hash-assigned shards. Three crates: `vairedb-coordinator` (client-facing
binary), `vairedb-core` (storage node binary), `vairedb-common` (anything that must be
byte-identical on both sides of the wire). `README.md` has the per-module tables; what follows
is the part you cannot get by reading one file.

### Two execution paths, one parse

Everything enters through `pgwire_handler`. A statement is parsed **once** in
`pgwire_handler/parser.rs` and then classified by `pgwire_handler/query_router.rs` into a
`QueryType`, which chooses the path:

- **Read path** (`SELECT`) — DataFusion plans the statement and the embedded Ballista
  scheduler (`coordinator/src/scheduler/`) distributes it. Each shard scan becomes a
  `RemoteDuckDbScanExec` that is *never* executed on the coordinator: it is serialized by
  `VairePhysicalCodec` and shipped to the core node, where it is rehydrated as
  `DuckDbScanExec` and turned into `SELECT <cols> FROM <shard_table> [WHERE pushed] [LIMIT n]`.
  No `GROUP BY` and no aggregate is ever pushed into DuckDB — joins, grouping and aggregation
  happen in DataFusion above the scans.
- **Write path** (`INSERT`/`UPDATE`/`DELETE`/`MERGE`/DDL) — no DataFusion at all. `write_sql_cl`
  rewrites the AST to DuckDB-compatible SQL, re-renders it to text, and `write_router` +
  `replication` dispatch it over gRPC to the core nodes, which execute it **verbatim**.

`parse_sql` hands the read path *rewritten* statements and the write path *verbatim* ones —
the pg-compatibility rewrites exist for DataFusion's planner and would corrupt a write. The
practical consequence: **a SQL expression has two verdicts, and every expression fix must be
checked on both paths.** Read-path rewrites live in `pgwire_handler/pg_*.rs` +
`compat_rewrite.rs` + `column_labels.rs`; write-path ones in
`write_sql_cl/duckdb_compat.rs`.

There is also a third, coordinator-local read context: catalog/introspection queries
(`vairedb_catalog.*`, `pg_catalog`) run on `local_ctx` rather than the distributed
`session_ctx` — see `catalog_routing.rs` and `introspection.rs`.

### Invariants that will bite you

- **One `sqlparser` in the tree.** `vairedb-coordinator` has no direct `sqlparser` dependency;
  it re-exports DataFusion's (`crate::sqlparser`, see `coordinator/src/lib.rs`). Always import
  the AST from there, never add the crate to `Cargo.toml`.
- **Shard table naming is a cross-node contract.** `util::shard_table_name` /
  `physical_base_name` produce `orders_shard3`, `sales.orders` → `sales_orders_shard3`. The
  coordinator's write rewrite and the core node's `CREATE TABLE` must agree byte for byte.
  Schema qualifiers are folded into the name (DuckDB gets one flat namespace) and the fold is
  not injective, which is why `CREATE TABLE` refuses a colliding logical name.
- **A UDF crosses the Ballista wire as a name and nothing else.** Any function whose
  PostgreSQL semantics differ from the engine default lives in `vairedb-common` and is
  registered through `distributed_functions::FAMILIES` — the single list. Registering on the
  planner only means the query is accepted and then fails on the executor; worse, a *shadowing*
  name registered on the planner only makes the other node silently resolve DataFusion's
  version and return a wrong answer. Add to `FAMILIES`, not to a call site.
- **Errors lose their type at the Ballista boundary**, so `vairedb-common/src/error.rs`
  re-derives a `VdbErrorCode`/SQLSTATE from the message text
  (`distributed_functions::error_code_of_message`). Message wording is load-bearing; the tests
  that pin it live beside the code that writes it.
- **Catalog** is `redb` at `<metadata_dir>/vairedb_meta.redb`, wrapped by
  `catalog::MetadataCatalog` and surfaced to SQL as `vairedb_catalog` virtual tables via
  `VaireDbCatalogSchema`. Metadata shapes are protobuf messages (`proto/vairedb/v1/catalog.proto`).
- **Cross-shard transactions have no commit protocol.** `allow_cross_shard_transactions` in the
  coordinator config gates whether such a `COMMIT` is refused or applied group-by-group (with
  partial-failure exposure).

## SQL compatibility doctrine

**PostgreSQL 16 is the contract.** DataFusion (read) and DuckDB (write) are implementation
layers — a form only they have is out of scope, and a DuckDB-only superset must *not* be
"fixed" into existence. `docs/specs/gap-analysis.md` is the single gap record: anything absent
from it is a claim that VaireDB agrees with PostgreSQL on the six axes it enumerates. Read
`gap-analysis.md` §2 before changing SQL behaviour, and update it in the same change.

The ranking that drives priority: ⛔ silently-wrong answers are the dangerous class, ❌ loud
refusals are open gaps, 🚫 is a written decision rather than backlog. A refusal is preferred
over a plausible wrong answer.

E2E convention for gaps: a **passing** test pinning today's behaviour plus an
`#[ignore = "gap: …"]` test asserting the PostgreSQL-correct target (which fails by
construction and *is* the definition of done). `make e2e` runs only the passing set. Every
refusal test must also assert, in the same test, that the neighbouring form which loses no
clause still answers — that is what keeps a refusal honestly scoped.

## Conventions

- Unit tests are inline `#[cfg(test)] mod tests` in the module they cover; cross-module
  integration tests go in `crates/<crate>/tests/*.rs`; behaviour a client can observe goes in
  `tests/e2e/tests/`. Shard-hash mirrors and `Describe`-type helpers used by e2e suites live in
  `tests/e2e/src/lib.rs` — reuse them rather than re-deriving the bucketing.
- Module docs carry the *why*, not the *what* — the existing files explain which rule was
  rejected and what failure mode a design prevents. Match that altitude when adding a module.
- Crates use `#![allow(clippy::module_inception)]`: `foo/foo.rs` re-exported through `foo/mod.rs`
  is the house style.
- SOLID/clean-code guidance is in the `solid-principles` skill (`.claude/skills/`);
  `docs/coding-agents/rust-module-code-refactor.md` is the standing refactor brief (one
  coordinator module per iteration).
- Docs: `docs/specs/` is the internal architecture set, indexed by `ARCHITECTURE.md`;
  `docs/vairedb.io/` is the published MkDocs site. Keep `docs/specs/*.md` high-level — no
  implementation detail. `README.md` is human-owned: propose changes, don't edit it unasked.
